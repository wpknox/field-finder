## B — Suspected Bugs (verify, then fix)

Ordered by severity. All were found by code reading, not observed live — each fix should
start by reproducing the problem (dev server + browser, or a targeted test).

### [FIXED 2026-08-26 · branch fix/audit-tranche-1 · `3585790` — live-verified] B1. Map pans on every click/drag after the first address search

**Severity: high (behavior contradicts a logged design decision)**

`src/lib/components/MapView.svelte:140-144` — the pan `$effect` guards on
`panVersion === 0` but also does a _tracked_ read of `center` (line 142). After the first
address search sets `panVersion` to 1, the guard never blocks again, and every subsequent
`center` change — map click, marker drag-end — re-runs the effect and calls `map.panTo`.
The decision log ([2026-03-19] `panVersion` entry) explicitly says pan must happen **only**
on address search / lat-lon input, never on click or drag.

**Fix:** read center untracked so only `panVersion` triggers the effect:
`const [lat, lon] = untrack(() => center);` (untrack is already imported).
**Verify:** dev server → search an address (map pans) → click elsewhere on the map →
the map must NOT re-center on the clicked point; drag the marker → no pan on release.

### [FIXED 2026-08-26 · branch fix/audit-tranche-1 · `420f59b` — LIVE VERIFICATION OUTSTANDING (CDL down)] B2. Overlay is placed at the _render-time_ center, not the _search-time_ center

**Severity: high (wrong data placement)**

`src/lib/components/MapView.svelte:182-184` captures `center` and `radius` with `untrack()`
inside the overlay `$effect`. The comment says "search-time snapshot," but this effect runs
when `tifBase64` arrives — i.e. **after** the multi-second CDL fetch completes. If the user
drags the marker or moves the radius slider while waiting, the raster (fetched for the old
bbox) is drawn at the _new_ center/radius: the overlay lands in the wrong place at the wrong
size.

**Fix:** snapshot `{ lat, lon, radius }` in `handleSearch` (`src/routes/+page.svelte`) at
the moment the request is sent, and pass it to MapView alongside `tifBase64` (e.g. a single
`searchResult = { tifBase64, lat, lon, radius }` prop replacing the bare string — this also
fixes B3 for free, since a fresh object identity always retriggers the effect).
**Verify:** search with a 10mi radius, immediately drag the marker a few miles away while
"Fetching crop data..." shows; when the overlay appears it must sit over the _original_
bbox rectangle position, not the marker's new position.

### [FIXED 2026-08-26 · branch fix/audit-tranche-1 · `420f59b` — LIVE VERIFICATION OUTSTANDING (CDL down)] B3. Repeating an identical search leaves the app stuck on "Downloading crop data..."

**Severity: medium-high (soft-locks the Search button)**

`src/routes/+page.svelte:157` assigns `tifBase64 = event.tifBase64`. If the user re-runs the
same search (same location/year/crops) and CDL returns byte-identical data, the assignment
is a same-value primitive write — Svelte 5 skips notification, MapView's overlay `$effect`
never re-runs, and nobody clears `loadingMessage` (the `finally` skips it because
`handedOffToMap` is true). The loading overlay persists and `SearchButton` stays disabled
(its `loading` prop derives from `loadingMessage`). Unconfirmed whether CDL responses are
byte-identical across requests (embedded timestamps may differ) — reproduce first.

**Fix:** the B2 fix (wrap results in a new object per search) resolves this structurally.
**Verify:** run the exact same search twice in a row; the second run must complete and clear
the loading overlay.

### [FIXED 2026-08-26 · branch fix/audit-tranche-1 · `5fbada7` — CDL_MAX_YEAR still 2024; 2025 availability unconfirmed] B4. Year range is hardcoded to 2024 — likely stale

**Severity: medium (missing newest data; gets worse every year)**

Three places pin the CDL year range at 1997–2024:

- `src/routes/api/search/+server.ts:31-32` (server validation)
- `src/lib/components/YearSelector.svelte:3-6` (dropdown + default)
- `src/routes/+page.svelte` (`year = $state(2024)`)

CDL releases the previous year's layer each winter; as of mid-2026 the 2025 layer should
exist. **First check** whether `GetCDLFile?year=2025` returns data (curl or CropScape UI),
then bump the max year in all three places — ideally to a single shared constant
(e.g. `CDL_MAX_YEAR` in `src/lib/crops.ts` or a new `src/lib/constants.ts`) so next year's
bump is one line. Also update the two range mentions in `CLAUDE.md` / `planning/features.md`.
**Verify:** dropdown offers 2025, a 2025 search renders an overlay, and year 2026 is
rejected server-side with a 400.

### [FIXED 2026-08-26 · branch fix/audit-tranche-1 · `009534f` — live-verified against the real outage] B5. Server has no timeout on CDL fetches — hung upstream hangs the search forever

**Severity: medium (turns the known "CDL API intermittently down" blocker into an indefinite spinner)**

`src/lib/server/cdl.ts` (`fetchCdlData`) and the `.tif` download in
`src/routes/api/search/+server.ts:62` call `fetch` with no `AbortSignal`. When NASS hangs
(documented blocker in `planning/features.md`), the SSE stream stays open and the client
spins forever with no error.

**Fix:** pass `AbortSignal.timeout(60_000)` (tune per step; the tif download may warrant
more) to each fetch; catch `TimeoutError` and send a distinct SSE error message like
"USDA CDL service is not responding — try again later." Optionally add a client-side
AbortController + Cancel button on the loading overlay (bigger task; can be separate).
**Verify:** unit-test `fetchCdlData` with a never-resolving mock fetch that respects the
signal; confirm it rejects after the timeout.

### B6. Geocoding failures are reported as "No results found"

**Severity: low (misleading UX)**

`src/lib/server/geocode.ts` returns `[]` for network errors and non-OK responses, so the
client (`SearchBar.svelte`) shows "No results found" when Nominatim is actually down. Also,
a non-OK `/api/geocode` response in SearchBar shows nothing at all.

**Fix:** have `geocode()` throw (or return a discriminated result) on failure; make the
endpoint return 502; show "Address lookup failed — try again" in SearchBar for non-OK
responses. Keep "No results found" only for a genuine empty result set.
**Verify:** existing geocode specs still pass, plus a new spec for the failure path.

### B7. SearchBar debounced results can arrive stale

**Severity: low (rare race)**

`src/lib/components/SearchBar.svelte` (`handleInput` → `debounceTimer`): the fetch response
is applied without checking whether `query` changed while the request was in flight. A slow
older response can overwrite results for a newer query. Fix by capturing the query at fetch
time and discarding the response if `query.trim()` no longer matches (same guard pattern
MapView uses with `currentTif`).

## C — Code Health / Cleanup (safe, mechanical)

### [FIXED 2026-08-26 · branch fix/audit-tranche-1 · `fef2432`] C1. Prettier drift — `npm run lint` currently fails

13 files unformatted (list via `npx prettier --check .`; includes `src/lib/server/cdl.ts`,
`src/routes/+page.svelte`, `src/routes/api/search/+server.ts`, three components, two specs,
plus markdown docs). Run `npm run format`, eyeball the diff, commit as a standalone
formatting commit. Consider a pre-commit hook or CI check afterward so it can't recur.

### C2. Remove the abandoned `georaster-layer-for-leaflet` dependency

The library was abandoned twice over (see decision log 2026-08-23) but is still in
`package.json` dependencies, with a leftover type shim at
`src/lib/types/georaster-layer-for-leaflet.d.ts`. Nothing in `src/` imports it.
`npm uninstall georaster-layer-for-leaflet`, delete the `.d.ts`, run `npm run check` + tests.

### C3. Dead database scaffold

`src/lib/server/db/` (drizzle + better-sqlite3, a template `task` table) is unused — no
route imports it. The decision log says defer DB until a feature needs it. Options: leave it
(harmless — it only throws on import, and nothing imports it) or delete `src/lib/server/db/`
and the placeholder `task` schema while keeping the deps/config for later. Recommend
deleting the placeholder `task` table at minimum, since it's template noise that will confuse
future sessions. Low priority.

### C4. Per-line `JSON.parse` in the SSE reader is unguarded

`src/routes/+page.svelte:152` — one malformed SSE line throws, aborts the whole read loop
into the generic catch, and discards any events still in the buffer. Wrap the parse in a
try/catch that skips the bad line (log to console). Small robustness win.

### C5. Waypoint popup HTML escaping is minimal

`src/lib/components/MapView.svelte:258` escapes only `"` in the waypoint name before
interpolating it into popup HTML. In the double-quoted-attribute context this happens to be
safe, but it's brittle — any future use of the name in a text context becomes an injection
point. It's self-XSS only (names come from the user's own localStorage). Harden by escaping
`& < > "` or by building the popup with DOM APIs (`document.createElement`) instead of an
HTML string. Low priority.

### C6. Nominatim rate limiter has a concurrency race

`src/lib/server/geocode.ts` — two concurrent requests can both pass `enforceRateLimit` and
hit Nominatim in the same second. For <20 users this is nearly theoretical; fix (serialize
via a promise chain: `lastRequest = lastRequest.then(...)`) only if bored. Lowest priority.

### C7. No automated e2e coverage

All 51 tests are pure-function unit tests (`geo`, `crops`, `cropStats`, `renderGeoraster`,
`cdl`, `coordinates`, `geocode`, `localStorage`). The SSE route handler, all Svelte
components, and the search→overlay flow have zero automated coverage — every regression so
far was caught by manual Playwright verification. A single Playwright smoke test (load page,
set test location 40.553950/-100.076157, search, assert overlay `<img>` appears with
width > 100) would catch the whole class of "renders wrong/never renders" regressions.
Caveat: it depends on the flaky live CDL API, so make it a separate opt-in script
(`test:e2e`), not part of `npm test`.

## D — UX Gaps (small, high-value polish)

- **D1. Year is not persisted** — location, radius, crop filters, opacity, sidebar state all
  survive reload; `year` silently resets to the default. Add `ff-last-year` to
  `src/lib/localStorage.ts` following the exact pattern of `radius`. Trivial.
- **D2. No way to cancel a running search** — pairs with B5. Client-side AbortController
  wired to a Cancel button on `LoadingOverlay`.
- **D3. Lat/lon direct entry gives no affordance** — typing valid coordinates just silently
  waits for Enter. A hint row ("Press Enter to go to 40.5540°N 100.0762°W") in the dropdown
  would make it discoverable.
- **D4. Area Summary vanishes during a new search** — `cropStats = []` is cleared when the
  old overlay is removed, before the new one arrives. Consider keeping the old stats greyed
  out until replacement. Cosmetic.
- **D5. Error toast text is generic** — most failure paths collapse to "Couldn't fetch crop
  data — try again." B5/B6 improve the two most common cases.

## F — Findings Added During Tranche 1 (2026-08-26)

Surfaced by the code-quality review of the B2/B3 fix. None block that fix; all are new work.

### F1. Overlay layer can be orphaned if two renders overlap

`src/lib/components/MapView.svelte` — the last staleness guard sits before
`await import('leaflet')` and `rasterToDataUrl()`, but the layer is not attached (and
`overlay` not assigned) until after them. If a newer `searchResult` lands in that window,
the newer run reads `overlay` as `undefined` and removes nothing; the older run then calls
`layer.addTo(map)` and its layer stays on the map with no reference left to remove it. The
older run also clears `loadingMessage`, wiping the newer run's progress message.

Currently unreachable because the Search button is disabled for the whole span — i.e.
guarded by UI, not by code. **Fix:** repeat the identity guard immediately before
`layer.addTo(map)`, and/or return a teardown from the `$effect`. Pre-existing shape (the
old code had the same race with `currentTif`), so this is not a regression from B2/B3.

### F2. `SearchResult` omits `year` and `crops`

`src/lib/searchResult.ts` — correctly scoped for B2/B3, but the planned **year comparison**
feature needs to know which year a rendered overlay represents. Decide deliberately when
building that feature rather than rediscovering it.

### F3. SSE payload is not runtime-validated

`src/routes/+page.svelte` — `JSON.parse` returns `any`, so `event.tifBase64` is unchecked
and `SearchResult`'s `tifBase64: string` is a compile-time claim only. A malformed `done`
event yields a truthy `searchResult` whose decode throws inside the effect, surfacing
"Failed to render crop overlay" instead of a data error. Pairs naturally with **C4** — add
a `typeof event.tifBase64 === 'string'` check when wrapping that `JSON.parse` in try/catch.

### F4. `loadingMessage` ownership is still split

`+page.svelte` hands ownership of the `$bindable` `loadingMessage` to `MapView` mid-flight.
B3 removed the specific way this got stuck, but the split ownership itself remains, with no
single owner. The structural fix is a render-token / state-machine refactor — out of scope
for tranche 1, worth considering before the overlay plumbing doubles for year comparison.
